## B-019
**n8n CLI 수동 실행이 서버와 포트 충돌** · 자동화 · 해결 (4단계 PR)

- **증상**: `docker compose exec n8n n8n execute --id WeeklyBriefing01`이 "Task Broker's port 5679 is already in use"로 아무것도
  실행하지 않고 끝났다(종료 코드도 애매해 놓치기 쉽다).
- **원인**: n8n 2.x의 `execute`는 자체 task broker를 띄우는데, 같은 컨테이너에서 서버가 이미 그 포트를 쓰고 있다.
- **수정**: 실행할 때만 포트를 바꾼다 — `-e N8N_RUNNERS_BROKER_PORT=5690`. `rules/server.md`에 명령을 그대로 적었다.

## B-018
**모델이 주간 집계를 '주말'이라고 씀** · 브리핑 · 해결 (4단계 PR)

- **증상**: 브리핑 초안 평가 10번이 전부 검사를 통과했는데, 발송문을 직접 읽어 보니 1번은 "주말 극장가에서 선두를 이어갔다"였다.
  표는 월~일 주간 집계라 틀린 말이다. 숫자 검사로는 잡히지 않는다.
- **원인**: 프롬프트가 "표에 없는 사실을 지어내지 말라"고만 했고, 집계 단위는 따로 말하지 않았다.
- **수정**: 프롬프트에 "표는 주간(월~일) 집계, '주말'·'개봉 첫날' 금지"를 넣고, `validate_draft`도 그 표현을 막는다(규칙을 코드에도).
  다시 10번 재서 0번.
- **재발 방지**: 단위 테스트, `tests/evals/README.md`에 "통과율만 보지 말고 발송문을 직접 읽을 것".

## B-017
**새 패키지 폴더가 Docker 이미지에 빠짐(적어 둔 규칙을 또 놓침)** · 배포 · 해결 (3단계 PR)

- **증상**: 3단계에서 `briefing/` 패키지를 만들고 compose를 올리자 api 컨테이너만 `ModuleNotFoundError: briefing`으로 재시작을 반복했다.
- **원인**: `docker/api.Dockerfile`이 COPY로 폴더를 하나씩 나열했다. 2단계에서 `rules/ci-deps.md`에 "새 패키지 폴더를 만들면 COPY에도
  추가할 것"이라고 적어 두었는데 그대로 놓쳤다. 규칙을 적는 것만으로는 막히지 않는 종류다.
- **수정**: `COPY . .`로 바꾸고, 뺄 것(`.env`, `web`, `tests`, 문서 등)은 `api.Dockerfile.dockerignore`가 정한다. 이제 새 폴더는 자동으로
  들어간다. 이미지 안을 확인해 코드만 있는 것(`.env`·문서 없음)을 봤다.
- **재발 방지**: 규칙이 아니라 구조로 막았다. 반대로 이미지에 넣으면 안 되는 폴더를 만들 때만 dockerignore에 추가한다(CLAUDE.md 쌍 표).

## B-016
**동시 승인 테스트가 발송 방어선을 실제로 시험하지 않음** · 테스트 · 해결 (3단계 PR)

- **증상**: 브리핑 통합 테스트 8개가 한 번에 통과했다. 의심스러워서 발송 방어선(`claim_send`의 `AND status = 'approved'`)을
  지우고 다시 돌렸는데도 **8개 모두 통과**했다.
- **원인**: "동시에 두 번 승인" 테스트는 그보다 앞의 `decide()` 조건부 UPDATE에서 두 번째 요청이 409로 걸러져 그래프가 한 번만
  재개됐다. `claim_send`가 필요한 건 그래프가 두 번 재개되는 경우 — 결정을 기록한 뒤 재개 전에 프로세스가 죽고, 재시도가 겹칠 때다.
- **수정**: 그 상황을 직접 만드는 테스트 2개를 추가했다(기록 후 재개 전 중단 → 재시도, 재시도 두 개 동시). 방어선을 지우면
  새 테스트가 실패하는 것을 확인하고 되돌렸다.
- **재발 방지**: 중복·경쟁을 막는 코드를 넣으면, 그 코드를 지웠을 때 실패하는 테스트가 있는지 직접 지워 보고 확인한다.

## B-015
**새 단위 테스트가 CI에서만 import 실패** · CI · 해결 (B-013 PR 안에서)

- **증상**: B-013 PR에서 `tests/unit/test_mcp_client.py`가 로컬은 통과, CI `python` 잡은 `ModuleNotFoundError: structlog`.
- **원인**: `tests/unit`은 표준 라이브러리만 쓰는 순수 모듈을 위한 곳이라 CI가 pytest만 설치한다. `mcp_client.py`는
  `logging_config`(structlog)를 import한다. 로컬 venv에는 모든 패키지가 있어서 드러나지 않았다.
- **수정**: 테스트를 `tests/mcp/`(전체 의존성을 설치하는 `deps` 잡에서 실행)로 옮겼다.
- **재발 방지**: `tests/unit`에 테스트를 추가할 때는 대상 모듈이 표준 라이브러리만 import하는지 본다. 로컬에서 확인하려면
  pytest만 깐 깨끗한 venv로 돌려야 한다 — 이번엔 CI가 병합 전에 잡았다.

## B-013
**MCP 도구 호출마다 약 280ms가 더 걸림** · MCP · 해결 (2026-10-17)

- **증상**: MCP 전환 후 같은 PC에서 잰 도구 지연(중앙값, 10회) — `imdb_sql` 3ms → 281ms, `imdb_search` 156ms → 436ms.
  평가에서도 MCP 쪽 항목이 1~3초씩 느렸다.
- **원인**: `langchain-mcp-adapters`의 `MultiServerMCPClient.get_tools()`가 만든 도구는 호출마다 세션을 새로 연다
  (초기화 왕복 + 호출 + 종료). 네트워크 홉 자체는 몇 ms다.
- **확인**: 세션 하나를 붙잡아 두고(`client.session()` + `load_mcp_tools(session)`) 다시 재면 6ms·164ms로 로컬과 거의 같다.
- **두는 이유**: 세션을 붙잡으면 MCP 서버가 재시작될 때 끊긴 세션을 다시 여는 로직이 필요하다. 배포(Railway)는
  로컬 도구를 써서 영향이 없고, MCP는 지금 compose에서만 쓴다.
- **수정(2026-10-17)**: `mcp_client.PersistentMcpSession` — 전용 백그라운드 태스크가 세션 하나를 열어 두고, 호출이 예외로
  실패하면(연결 문제) 새 세션으로 한 번만 다시 부른다. 어댑터가 세션에서 쓰는 `list_tools`·`call_tool`만 흉내 내서
  `load_mcp_tools()`에 넘긴다. 세션을 요청 태스크에서 열고 다른 태스크에서 닫으면 anyio 에러가 나서 소유 태스크를 따로 뒀다.
- **결과**: `imdb_sql` 281ms → 12ms, `imdb_search` 436ms → 169ms(로컬 3ms·156ms와 거의 같음).
  MCP 서버를 재시작해도 다음 호출이 자동으로 다시 붙는다 — 스크립트로 서버를 껐다 켜고, compose에서 `restart mcp` 후
  웹 질문 2개(imdb_sql·kobis_search)가 출처와 함께 정상(로그 `mcp.reconnect` 1번).
- **재발 방지**: `tests/mcp/test_mcp_client.py`(가짜 세션) — 세션 하나 공유, 끊기면 한 번 재시도, 두 번째도 실패하면 예외,
  동시에 실패해도 재연결은 한 번. `rules/tools.md` "지연과 세션"에 쓰기 도구를 추가하면 재시도를 다시 볼 것을 적었다.

## B-012
**MCP 결과 형태가 달라 출처가 사라질 뻔함** · MCP · 해결 (2단계 PR)

- **증상**: 출시 전에 발견했다. 어댑터 코드를 읽어 보니 MCP 도구의 `ToolMessage.content`는 문자열이 아니라
  블록 목록(`[{"type": "text", ...}]`)이고, `imdb_search`의 artifact는 `list[Document]`가 아니라
  `{"structured_content": ...}`였다.
- **원인**: `sources.py`가 문자열·Document만 처리했다. 그대로 두면 웹 출처는 사라지고(문자열이 아니라 빈 결과),
  KOBIS·SQL은 에러 응답에도 고정 출처가 붙고(`startswith("[TOOL_ERROR")` 검사를 건너뜀), IMDB 출처도 사라진다.
- **수정**: `sources.as_text()`로 블록 목록을 문자열로 만들고, IMDB는 두 artifact 형태를 모두 읽는다. MCP 서버는
  `imdb_search`가 `structuredContent`로 순위·제목을 보낸다.
- **재발 방지**: `tests/unit/test_sources.py`의 `TestMcpShapes`, 어댑터를 실제로 거치는 `tests/mcp/`의 출처 테스트.

## B-011
**인자 검증에 실패한 도구 호출에도 출처 칩이 붙음** · 서버 · 해결 (2단계 PR)

- **증상**: `kobis_search`에 연도 `"24"`처럼 잘못된 인자가 오면 검증 오류 메시지와 함께 "영화진흥위원회" 출처 칩이
  붙었다. 근거가 아닌데 출처처럼 보인다. 로컬 도구에서도 있던 문제다(ToolNode로 재현).
- **원인**: 검증 실패는 LangChain이 `status="error"` ToolMessage로 바꿔 모델에 주는데, 메시지가 `[TOOL_ERROR`로
  시작하지 않아서 `sources.extract_sources()`의 에러 검사를 지나갔다.
- **수정**: `status == "error"`면 출처를 만들지 않는다.
- **재발 방지**: `TestErrorStatus`.

## B-010
**Windows에서 만든 락에 Windows 전용 패키지가 섞임** · 의존성 · 해결 (2단계 PR)

- **증상**: `mcp`를 추가하고 `scripts/gen_lock.py`를 돌리자 `requirements.txt`에 `pywin32==312`가 들어갔다. 리눅스
  (Railway·Docker)에는 이 패키지가 없어 `pip install -r requirements.txt`가 실패했을 것이다. 기존 락에도
  `colorama==0.4.6`(Windows 전용 조건)이 들어 있었다 — 순수 파이썬이라 설치는 돼서 드러나지 않았다.
- **원인**: `gen_lock.py`가 의존성의 플랫폼 조건(`sys_platform == "win32"`)을 스크립트를 돌린 PC 기준으로 판단했다.
- **수정**: 배포 환경(linux x86_64)을 고정한 `TARGET_ENV`로 판단한다. 락은 85개(`colorama`가 빠짐).
- **재발 방지**: `rules/ci-deps.md`에 적었다. CI `deps` 잡이 리눅스에서 락을 실제로 설치한다.

## B-009
**배포 서버에서 레이트리밋이 전혀 걸리지 않음** · 서버 · 해결 (PR #7, #8 · Railway·Vercel에 `PROXY_SECRET`)

- **처음 추정(2026-10-16)**: 코드를 읽다가 "모든 방문자가 프록시 주소 하나로 묶여 분당 10회를 나눠 쓴다"고 봤다.
- **실제로 재 보니 반대였다(2026-10-17)**. 배포 서버에 캐시된 질문을 보내 확인했다(LLM 비용 없음).
  | 시험 | 결과 |
  |---|---|
  | Railway 직접 6번 + Vercel 경유 6번 번갈아 | 429 없음 — 두 경로가 한 통을 쓰지 않는다 |
  | Vercel 경유만 12번 | 429 없음 |
  | Railway 직접 25번(1분 안) | 429 없음 |
  | Railway 직접 **15개 동시**(0.4초) | **429 없음** — 1분 구간 경계 때문도 아니다 |
  | 같은 코드를 로컬에서 12번 | 11번째부터 429 — 코드는 정상 |
  즉 묶이는 게 아니라 **아예 제한이 안 걸렸다.** 비용 공격(분당 수백 번의 LLM 호출)을 막는 장치가 없던 상태다.
- **원인**: 키 함수 `get_remote_address`는 TCP 접속 주소를 쓴다. 배포에서는 그 상대가 Railway 프록시이고 주소가
  요청마다 달라 매번 새 키가 됐다. 서버가 여러 개라는 가설은 25번·15번 시험에서 맞지 않았다(2개면 20번째쯤 걸린다).
  Vercel 경유 요청도 백엔드가 보는 주소는 Vercel이라 방문자를 구분할 수 없다.
- **수정**: `ratelimit.rate_limit_key()`(순수 함수)로 키를 정한다.
  1. `route.ts`가 `x-real-ip`(Vercel이 덮어쓰는 방문자 IP)를 `X-Client-IP`로, 공유 비밀값을 `X-Proxy-Secret`으로 보내고,
     백엔드는 `PROXY_SECRET`과 맞을 때만 믿는다.
  2. 아니면 `X-Forwarded-For`의 맨 오른쪽(우리 쪽 프록시가 붙인 접속 주소). 3. 아니면 TCP 주소. (2는 아래 재측정에서 틀린 것으로 드러나 뺐다)
  로그에는 IP 대신 `rate_key_source`만 남긴다.
- **로컬 통합 시험**: 서로 다른 방문자 15명 동시 → 429 0개, 같은 방문자 15번 → 429 5개,
  비밀값 없이 IP 위조 15번 → 429 5개(위조가 통하지 않음).
- **배포 후 재측정(2026-10-17, `PROXY_SECRET` 설정 후)**:
  | 시험 (15개 동시) | 결과 |
  |---|---|
  | Vercel 경유 | 429 5개 ✅ |
  | Vercel 경유 + `X-Forwarded-For`·`X-Real-IP` 위조 | 429 5개 ✅ (Vercel이 덮어씀) |
  | Railway 직접 | **429 없음** ❌ |
  | Railway 직접 + `X-Forwarded-For` 위조 | 429 없음 ❌ |
  방문자 경로(Vercel)는 고쳐졌지만, **`X-Forwarded-For` 맨 오른쪽도 Railway 프록시 주소라 요청마다 달랐다.**
  "맨 오른쪽 = 실제 접속 주소"라는 가정이 틀렸다.
- **2차 수정**: `X-Forwarded-For` 규칙을 지우고, 비밀값이 설정된 서버는 프록시를 거치지 않은 `/api/chat`을 **403으로
  거절**한다. 백엔드 주소로 바로 오는 요청은 방문자를 구분할 방법이 없기 때문이다. 정상 사용자는 모두 Vercel을 거친다.
  로컬 시험: 비밀값 없는 직접 호출 → 403 5/5, 틀린 비밀값 + IP 위조 → 403 5/5, 방문자 15명 → 200, 같은 방문자 15번 → 429 5개.
- **최종 확인(2026-10-17, PR #8 배포 후, 배포 서버)**:
  | 시험 | 결과 |
  |---|---|
  | 실제 사이트에서 질문 | 200, `imdb_sql` 호출, 출처 칩 있음 |
  | Railway 직접 10개 | 403 10개 |
  | Railway 직접 + `X-Client-IP`·`X-Proxy-Secret`·`X-Forwarded-For` 위조 10개 | 403 10개 |
  | Vercel 경유 15개 동시 | 200 10개, 429 5개 |
  | Vercel 경유 + 헤더 위조 15개 | 200 10개, 429 5개 |
- **재발 방지**: `tests/unit/test_ratelimit.py`(위조·비밀값 불일치·빈 비밀값 포함). `rules/server.md` "레이트 리미팅"에
  판단 순서와 이유를 적었다. 레이트리밋을 바꾸면 로컬이 아니라 **배포 서버에서** 동시 요청으로 확인할 것.
