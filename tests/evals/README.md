# 에이전트 평가 (Evals)

골든 데이터셋 기반 회귀 평가. 프롬프트/모델/도구 변경 시 품질이 떨어지지 않는지 자동으로 검증합니다.

## 구조
- `golden_dataset.json` — 평가 항목(질문, 기대 도구, 기대 키워드, rubric)
- `run_evals.py` — 평가 러너

## 실행
프로젝트 루트에서:

```bash
# 전체 평가 (LLM-as-judge 포함, OpenAI API 사용)
python -m tests.evals.run_evals

# judge 생략 (채점 비용만 절약 — 에이전트 본체는 실제로 호출되므로 무료가 아니다)
python -m tests.evals.run_evals --skip-judge

# 특정 항목만 실행
python -m tests.evals.run_evals --ids imdb-001 kobis-001
```

## 평가 기준
각 항목은 다음을 검증합니다:
1. **도구 호출(tools_ok)** — `expected_tools` 중 하나라도 호출했는지
2. **키워드(keywords_ok)** — `expected_keywords` 중 하나(또는 전부) 포함됐는지
3. **judge_score** — (옵션) GPT 채점관이 rubric 기준 1~5점

모두 통과 + judge ≥ 4점이면 PASS.

> **judge 호출이 실패하면 해당 항목은 실패 처리됩니다.** 예전에는 `judge_score`가 `None`으로
> 남아 자동 통과되면서 평가가 조용히 무력화되는 fail-open 구조였습니다. `judge_failed` 플래그가
> 이 구멍을 막습니다.

> **평가도 서버와 같은 입력을 씁니다.** 질문 앞에 오늘 날짜 문장(`format_date_context(today_kst())`)을
> `SystemMessage`로 넣고, 채점관 프롬프트에도 같은 날짜를 줍니다. `kobis-006`("지난 주 박스오피스")처럼
> 정답이 날짜에 따라 바뀌는 항목은 채점관이 오늘을 모르면 판정할 수 없기 때문입니다.
> 그런 항목의 rubric은 **특정 날짜를 적지 말고** "주어진 오늘 날짜의 직전 주"처럼 상대적으로 쓸 것 —
> 날짜를 박아 두면 다음 주부터 틀린 기준이 됩니다.

> **`--skip-judge`는 완전 무료가 아닙니다.** 채점 비용만 없앨 뿐 에이전트 본체는 모든 항목에 대해
> 실제로 OpenAI·Tavily·KOBIS를 호출합니다. 비용 0으로 돌릴 수 있는 것은 `pytest tests/unit/`뿐입니다.

## 새 항목 추가
`golden_dataset.json`에 객체 추가:
```json
{
  "id": "고유-id",
  "question": "사용자 질문",
  "expected_tools": ["kobis_search"],
  "expected_keywords": ["키워드1", "키워드2"],
  "expected_keywords_any": true,
  "rubric": "이 답변이 가져야 할 조건을 한 문장으로"
}
```

### 같은 대화에서 이어 묻기 — `history`

```json
  "history": ["쇼생크 탈출의 감독은 누구야?"],
  "question": "쇼생크 탈출 감독이 누구야?",
```

`history`의 질문들을 같은 대화(thread)에서 먼저 실행한 뒤 `question`을 묻는다. 도구 호출은 **마지막
질문의 것만** 센다. 항목마다 새 대화로 한 번만 묻던 방식으로는 "이미 답한 질문을 다시 하면 도구 없이
답해 출처가 사라지는" 문제가 보이지 않았다(`multiturn-001`).

`expected_keywords_any`(any/all)와 `rubric` 작성을 잊지 말 것. 거절 규칙처럼 **경계**를 다루는
항목은 양쪽 방향을 모두 세운다 — `refusal-001`(거절해야 함)과 `refusal-002`(거절하면 안 됨).

### `imdb_search` 항목에는 `corpus_evidence`

```json
  "expected_tools": ["imdb_search"],
  "expected_keywords": ["프랭크", "다라본트"],
  "corpus_evidence": ["The Shawshank Redemption", "Frank Darabont"],
```

답의 근거가 되는 **영어** 문자열을 적는다(코퍼스가 영어다). `tests/unit/test_imdb_data.py`가
이 필드가 있는 모든 항목에 대해 문자열이 코퍼스에 실제로 있는지 확인하고, `expected_tools`에
`imdb_search`가 있는데 이 필드가 없으면 실패한다.

이유: 평가는 "답이 맞는가"만 보고 "답이 코퍼스에서 왔는가"는 보지 않는다. 예전 PDF는 칸 너비에서
글자가 잘려 'Shawshank'가 한 번도 없었는데, 모델이 사전지식으로 답해 IMDB 항목이 전부 통과했다.

`imdb_sql` 항목에는 강제하지 않는다. "1990년대 몇 편"의 답 39는 이 CSV에서만 나오는 값이라
모델이 기억으로 맞힐 수 없고, 키워드 검사가 곧 도구를 썼다는 증거다.

> 이 검사는 **답이 코퍼스에 있다**만 보장한다. **검색이 그걸 찾아오는지**(적중률)는 별개다.
> 예: 검색어 "쇼생크 탈출 감독"을 그대로 넣으면 상위 8편에 쇼생크가 없다(코퍼스가 영어). 실제로는
> 모델이 제목을 영어로 바꿔 검색해서 적중하지만, 그건 모델 행동이지 보장이 아니다.

## 검색 적중률 — `run_retrieval.py`

골든셋 평가는 **최종 답변**을 본다. 모델이 기억으로 맞혀도 통과한다. 이 스크립트는 그 앞 단계인
**검색이 정답 영화를 가져오는가**만 따로 잰다. LLM은 부르지 않고 임베딩만 호출한다.

```bash
python -m tests.evals.run_retrieval          # 유형별·언어별 표 + 상위 3편 밖 질문
python -m tests.evals.run_retrieval --all    # 질문마다 전부
```

- 질문은 `retrieval_set.json`(50개). 같은 영화를 영어·한국어로 짝지어 넣어 언어 차이가 보이게 했다.
- **원문 기준**이다. 사용자 질문을 그대로 검색어로 쓴다. 실제 서비스에서는 모델이 검색어를 바꿔
  넘기므로, 낮게 나온 유형은 "모델의 번역에 기대고 있는 약점"으로 읽는다.
- 정답은 제목으로 적는다(CSV의 원제 그대로). 오타는 `test_imdb_data.py`가 잡는다.
- 정렬·집계 질문("평점 1위")은 넣지 않는다. SQL 도구의 일이라 검색이 못 찾는 게 정상이다.

### 기준선 (2026-10-01, 커밋 4a99949)

| 구분 | 개수 | Hit@1 | Hit@3 | Hit@8 | MRR |
|---|---|---|---|---|---|
| 전체 | 50 | 0.56 | 0.64 | 0.76 | 0.61 |
| 영어 질문 | 22 | 0.91 | 0.95 | **1.00** | 0.94 |
| 한국어 질문 | 28 | 0.29 | 0.39 | **0.57** | 0.36 |
| 한국어 제목 | 10 | 0.20 | 0.20 | **0.30** | 0.22 |

읽는 법: 영어로 물으면 전부 찾고, 한국어 제목으로 물으면 10개 중 3개만 찾는다. 한국어 질문은
한국 영화(Ah-ga-ssi, Oldeuboi 등)로 끌려가는 경향이 있다 — 배우 이름 같은 한국어 로마자 표기에
가까워져서로 보인다. 'Parasite'처럼 데이터에 없는 통용 제목은 영어여도 8번째로 밀린다.

**BM25(하이브리드)로는 이 차이가 안 메워진다.** 한국어 질문의 단어가 영어 문서에 하나도 없기
때문이다. 효과가 있을 후보는 검색어를 영어로 바꾸는 것, 또는 문서에 한국어 제목·통용 제목을 붙이는 것.
검색 설정을 바꿀 때는 이 표와 비교할 것.

### 실제 기준 (`--actual`, 같은 날)

에이전트를 실제로 돌려 모델이 `imdb_search`에 넘긴 검색어와 그 결과로 다시 쟀다. LLM을 부르므로
과금된다(질문 50개, 대략 수십 센트). 비교는 `imdb_search`를 부른 질문 40개끼리.

| 구분 | 검색함 | 원문 Hit@8 | 실제 Hit@8 | 원문 MRR | 실제 MRR |
|---|---|---|---|---|---|
| 전체 | 40/50 | 0.72 | **0.97** | 0.61 | **0.94** |
| 한국어 질문 | 19/28 | 0.42 | **0.95** | 0.26 | **0.92** |
| 한국어 제목 | 8/10 | 0.12 | **1.00** | 0.03 | **1.00** |

- **모델이 검색어를 영어로 바꿔서 원문 기준의 약점이 거의 가려진다.** 검색 40번 중 한국어 검색어는
  2번뿐이었다("쇼생크 탈출 감독" → `The Shawshank Redemption director`).
- **남은 실패는 한국어 줄거리 묘사**다. 제목을 떠올리지 못한 "요리하는 쥐"는 한국어 그대로 검색해
  못 찾았다. 같은 유형 2개("공룡을 복제한 테마파크" 등)는 검색 대신 웹 검색으로 갔다.
- **검색을 안 한 10개는 대부분 정상 경로다.** 한국 영화를 한국어로 물으면 KOBIS(5개), 감독 작품 목록은
  SQL(2개, 오히려 더 정확), 줄거리 묘사는 웹 검색(3개).
- 그래서 **한국어 제목을 데이터에 추가할 근거는 약하다** — 제목은 모델이 이미 번역한다. 남은 틈은
  "검색어를 영어로 쓰라"는 도구 설명으로 메울 수 있는 크기다.
- 한 번 돌린 결과다. 모델 출력이 매번 조금씩 다르므로 소수 차이에 의미를 두지 말 것.

### 도구 설명에 "검색어는 영어로"를 넣은 뒤

위 결과로 `imdb_search` 설명에 "자료가 영어라 검색어는 영어로, 제목을 모르는 줄거리 묘사도 영어
키워드로 먼저 여기서"를 추가하고 실제 기준을 다시 쟀다.

| | 수정 전 | 수정 후 |
|---|---|---|
| imdb_search 호출 | 40 | 42 |
| 그중 한국어 검색어 | 2 | **0** |
| 실제 Hit@8 / MRR | 0.97 / 0.94 | **1.00** / 0.96 |
| 줄거리 묘사 검색 | 6/8, "요리하는 쥐" 못 찾음 | **8/8 모두 찾음** |
| 웹 검색으로 우회 | 3 | 1 |

KOBIS로 가는 5개(한국 영화를 한국어로 물은 경우)는 그대로다. 정상 경로라 손대지 않았다.

## 알려진 흔들림

- `kobis-005`(주말 박스오피스)는 judge 점수가 통과선(4점) 근처를 오간다. 답변은 매번 같은 기간·같은
  1위인데 한 번은 2점을 받았다(같은 날 다시 3번 돌려 5·4·4점). 이 항목이 혼자 떨어지면 먼저 다시
  돌려 볼 것. judge와 사람 판정의 일치도는 재지 않았다.

## 종료 코드
- `0` — 전체 통과
- `1` — 하나 이상 실패 (CI에서 회귀 차단용)
